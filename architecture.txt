# EmONC Mentorship System — Frontend Architecture

We will build the frontend around four actual user roles, one shared dashboard layout, reusable sidebar components, and independent role-specific pages.

The most important architectural decision is this:

The sidebar is shared, but the navigation, pages, features, and permissions are specific to each role.

This means we can change the Mentor sidebar without accidentally changing the Mentee sidebar, and we can add new pages without turning the application into one large, difficult-to-maintain component.

| Mentor                           | Mentorship activities, cohorts and mentee progress       |

## 7. Routing architecture

We will use React Router.

Each role gets a route prefix, keeping its pages organized and predictable.

| Role               | Route prefix     | Example                   |
| ------------------ | ---------------- | ------------------------- |
| County Mentor / RH | `/county-mentor` | `/county-mentor/overview` |
| Mentor             | `/mentor`        | `/mentor/learning-plan`   |
| Mentee             | `/mentee`        | `/mentee/schedule`        |
| Developer / Admin  | `/developer`     | `/developer/overview`     |

Conceptually:

```
<Routes>
  <Route element={<ProtectedRoute />}>
    <Route
      path="/county-mentor"
      element={<RoleRoute allowedRoles={['county-mentor']} />}
    >
      <Route element={<DashboardLayout />}>
        <Route index element={<Navigate to="overview" replace />} />
        <Route path="overview" element={<OverviewPage />} />
        <Route path="mentors" element={<MentorsPage />} />
      </Route>
    </Route>
  </Route>
</Routes>
```

This is illustrative; the final router will compose the role-specific route definitions rather than putting every page in one central file.

## 8. Authentication and authorization

We should keep three responsibilities separate:

1. Authentication: Who has signed in?
2. Role resolution: Which of the four roles belongs to that user?
3. Authorization: Which operations and resources can that role access?

The frontend will use the authenticated user's assigned role to select the correct dashboard. The backend must independently enforce permissions.

For example, a Mentee should not be able to access County Mentor management endpoints simply by manually entering a URL.

## 10. Architectural rules we should maintain

- Never create a separate sidebar component for every role.
- Never put all role pages inside one folder.
- Never put every route inside one enormous router file.
- Never use scattered role-based conditions throughout page components.
- Keep role-specific business logic inside its own feature.
- Keep genuinely reusable components in `components/shared`.
- Keep API calls in services rather than directly inside every page.
- Use Carbon React consistently for UI components and Carbon Icons for navigation.
- Do not create placeholder pages just to make the sidebar links work.
- Keep backend authorization separate from frontend navigation visibility.
